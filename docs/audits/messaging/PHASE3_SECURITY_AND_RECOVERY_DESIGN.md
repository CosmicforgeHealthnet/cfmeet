# Phase 3 security policy and protocol proposal

Status: local WebAuthn/OS unlock selected by the owner on 2026-11-24; implementation and release acceptance still pending. The owner explicitly allows an authenticator prompt. Backup remains proposed and inactive. Production incident root cause remains unconfirmed. Engineering branch: `codex/messaging-reliability-phase3`, draft PR #175. This document explicitly distinguishes the reliability implementation from the remaining lifecycle and transfer work.

## Implemented reliability scope

The worker records initial group epoch/method for newly generated devices and treats legacy provenance as unknown. A prior epoch alone is no longer BEFORE_JOIN; registration timestamps do not decide history availability. Existing success records survive duplicate deliveries. Failed frames remain retryable through a durable, bounded queue (256 records/conversation); failures rotate for fairness and commits take priority. The delivery cursor and a contiguous processing position are persisted separately. Gaps stop progress rather than advancing over missing rows; initial visibility can start above sequence 1. Failed commits block later processing. State/outcomes/cursors are committed atomically, with in-memory state restored after batch persistence failure. Worker RPCs are serialized. A failed Welcome join is not consumed.

The initial processing migration imports up to 256 old failed/unverified BEFORE_JOIN records into the retry queue. Larger legacy failure sets require a paginated migration before release; do not declare arbitrary historic failures recovered. An already advanced MLS state cannot reconstruct erased epoch secrets. The v1 transfer now refuses overflow and empty history; this prevents false success but does not provide the requested v2 large-history feature. No server message, device row or key is deleted by this change. The shipped WASM bytes remain unchanged; the worker is repackaged with existing content-addressed artifact tooling. No past epoch retention or cryptographic protocol change has been activated.

## Selected logout policy: local WebAuthn/OS unlock

Retaining a non-extractable browser CryptoKey is insufficient: any same-origin script with access to the profile can use it. A boolean signed-in flag or browser memory cache is also not an authorization boundary. Simply removing wipe from logout would expose readable history to a later user of a shared profile. Therefore the existing destructive logout is not replaced until the unlock policy is reviewed.

Required invariants:

- Account UUID, Account installation/device UUID, auth session UUID, persistent Messaging UUID, per-group MLS leaf, and realtime/client session are distinct and independently auditable.
- Ordinary sign-out/expiry ends every session credential, closes workers in all tabs and denies network authority. It does not terminally revoke persistent Messaging identity under the proposed policy. Retained history must be cryptographically locked, not hidden in the UI.
- A fresh sign-in plus proof of the same unrevoked trusted installation unlocks the retained history. Email/account selection alone is insufficient. A lost/terminally revoked installation can only register a new identity and recover through an independent approved source.
- Explicit removal, compromise, password/security revocation and sign-out-everywhere retain strong, well-defined terminal behavior. A terminal UUID is never reused or reactivated. Local wiping is best effort; a remote revoke cannot guarantee deletion from an offline compromised browser. Membership removal/rekey and server authorization enforce future exclusion.

The owner selected option 1 below. Option 2 is rejected for this implementation; it is retained here only as design context, not an open permission request:

1. **Local user-verifying unlock:** wrap the random local history key with a WebAuthn PRF-derived secret (or native OS user-presence-protected storage). Fresh sign-in and device proof gate authorization; biometric/PIN unlock gates local access. No server unlock secret. Web support, credential loss/rotation and native parity require testing. System authenticator prompts change the unlock experience and need an explicit exception to the unchanged-UX constraint. A PIN-only JavaScript wrapper or passwordless email code must not be substituted as a cryptographic secret.
2. **Split unlock:** combine an independently generated local 256-bit secret and an authentication/device-proof-gated server-held random share with a reviewed HKDF envelope protocol. Neither share alone decrypts history; the service never has the local share or history key. On logout drop the combined key and server share from every tab; keep only sealed history plus the local share. Unlock grants are account/installation/device/epoch bound, non-cacheable and require a live unrevoked session and proof. The server share is secret key material even though it cannot decrypt alone. This option needs explicit interpretation/review of the user's prohibition on server-held private decryption keys, a threat model for service compromise plus stolen browser storage, recovery/rotation, and side-channel review. Do not activate it by treating it as an ordinary session token.

Selected direction: option 1. Preserve the current safe behavior on unsupported authenticators until a fallback is reviewed; do not silently retain decryptable history without PRF/user verification. The authenticator-prompt exception has been approved. That resolves the product policy choice; it does not establish that envelope migration, cross-tab key eviction or backend lifecycle bindings have been implemented. ADRs 0057/0060/0067 should be amended only after selecting the policy, rather than documenting a new lifecycle as already operational.

## Bounded past-epoch policy

A separate crypto change should use the pinned OpenMLS past-epoch APIs with a maximum of two retained epochs and a maximum age of 24 hours as candidate limits for review. Epoch count alone is not a time limit in a quiet group. Delete expired state before processing/open and after commit processing, update serialized configuration of existing groups without changing device identity, and validate clock rollback behavior. Extended offline catch-up should normally process authoritative applications/commits in sequence; retention only handles bounded reorder/retry windows. Never retain all old device-state snapshots: those include unrelated groups and KeyPackage material and broaden compromise exposure. Removal/rekey security, malicious replay, expiry and mixed serialized versions need dedicated real-core tests before rebuilding WASM and SDKs. This proposal has not activated retention or recovered previously erased secrets.

## Version 2 encrypted transfer implementation contract

The existing v1 transfer remains a compatibility fallback only for complete archives that fit. V1 sources now fail explicitly on overflow/empty coverage. V2 must be separately negotiated (`historyTransferVersions: [1,2]`); an older client must never interpret a partial v2 page as v1 completion.

A v2 request binds transfer UUID, source/target device UUIDs, principal and tenant/app/environment scope, expiry, target single-use HPKE key, archive version and snapshot ID. Source and target must be active authorized devices throughout request, upload, download and completion; device revocation cancels the transfer and removes server sealed chunks according to retention policy. Target request authorization and comparison-code verification remain at least as strong as v1. Reuse audited crypto primitives, not a handwritten cipher/key exchange.

Source creates a stable local encrypted snapshot index without exporting MLS state. The signed/encrypted manifest contains snapshot/transfer binding, schema version, per-conversation eligible record count and sequence coverage, gaps/unsupported records, attachment descriptor coverage, chunk count and ordered digests, total bytes and explicit COMPLETE/PARTIAL/EMPTY source coverage. This describes source possession; it must never assert possession of all messages ever sent simply from the server's maximum sequence. A zero-record source returns EMPTY rather than a successful recovery claim.

Each sealed chunk includes the manifest digest, index, previous chunk binding, record identities and source/target/scope/snapshot/expiry binding under authenticated encryption and source authentication. Limit decoded plaintext to 256 KiB and encoded ciphertext to a server-enforced maximum. Use UTF-8 byte counts, a strict decompression budget (prefer no compression initially), maximum total transfer bytes and finite TTL. Bound per-account concurrent transfers and disk usage. Include sent and received application records, encrypted attachment descriptors/keys only within the target-encrypted envelope, and attachment ciphertext references/digests. Do not copy deleted/expired/hidden content into another device contrary to authoritative visibility/retention rules.

API additions: initiate/status/capabilities; write immutable manifest; idempotent put/get indexed chunk; report durable received indexes; finalize with manifest digest and coverage confirmation; cancel. Server stores only sealed objects and opaque metadata, validates bounds/device authority, checks chunk digests and indexes, and refuses completion if required chunks are missing. Client verifies every authenticated binding and complete manifest coverage before reporting recovery complete; a service cannot make an incomplete archive complete just by setting status. Full target receive progress and the single-use transfer private key must survive browser restart in protected local state; current `beginTransfer` is not a sufficient resumability contract by itself.

Database: additive v2 transfer row/version/capabilities/manifest digest/expiry plus immutable chunk rows or object references, size/digest, source/target binding, idempotency uniqueness `(transfer_id, chunk_index)`, receive bitmap/checkpoint and terminal reason. Separate migrations with no existing ciphertext rewrite. Old servers reject v2 through capability checks; new clients fall back to complete bounded v1 only. New servers continue to serve v1. Terminal revocation and expiry must cancel both versions. Import chunks transactionally and idempotently, preserve already readable local records, resolve immutable message ID/sequence conflicts safely, and persist checkpoint with imported records. Cross-platform Rust/TypeScript/Dart bindings and shared test vectors are required; SDK primitives alone are not native app support.

Required v2 tests: many conversations with >512 KiB, non-ASCII size bounds, exact boundary, empty/partial source, complete sent/received and attachment metadata, restart of each peer during every phase, source snapshot mutation, duplicate/reordered/missing/corrupt chunks, wrong source/target/principal/scope/manifest, expiration, revocation mid-transfer, disk quota, immutable overwrite attempts, mixed versions, retention changes and duplicate-free resumable import. Security review precedes enabling automatic background transfer.

## Separate optional encrypted account-history backup proposal

Backups remain off. This proposal is not a production capability or implemented protocol.

Generate a client-controlled random recovery root with at least 256 bits of entropy; provide an explicit owner-approved recovery artifact and verify it can restore before relying on it. Derive a versioned backup wrapping key with domain separation; encrypt a random per-snapshot data key and authenticate manifest/chunks and account/snapshot/version bindings. Store only authenticated ciphertext and opaque storage references on the service. Never send the recovery root, unwrapped keys or plaintext archives to servers or telemetry. Prefer random recovery material over a low-entropy password; any password-derived option requires reviewed memory-hard KDF parameters, salt and offline attack analysis. No silent escrow or account-password fallback.

A new device signs in normally, obtains account-scoped backup ciphertext, and locally uses the recovery secret to verify/decrypt the manifest and all chunks. Device authorization is necessary but does not replace the recovery secret. Password reset changes online authentication only: it cannot decrypt an old backup. Losing all valid device copies and the recovery secret is unrecoverable; disclose this before activation. A stolen recovery secret plus backup ciphertext compromises that backup; rotate recovery material and rewrap/re-encrypt retained snapshots, revoke obsolete access, and assess already downloaded copies, which cannot be remotely erased.

Rotation: version recovery roots and wrapped snapshot keys, bind the version in authentication, checkpoint rotation and verify a new restore before retiring the old wrapping record. Retention/deletion: owner-selected finite snapshot retention, hard byte quota, encrypted tombstones and object cleanup, legal/retention policy review, documented replica/backup expiry; user deletion cannot revoke copies already downloaded. Treat manifest metadata and access logs as sensitive. Backup storage cost is approximately retained ciphertext bytes plus manifests/chunk overhead, replication and egress; deduplication must not expose plaintext-derived cross-account identifiers. Before pricing, measure actual ciphertext growth and restore bandwidth; no fabricated monetary estimate is provided. Native secure storage and recovery UX need iOS/Android implementation and physical-device tests.

Acceptance gates: independent cryptographic/protocol review; owner approval of recovery-key UX and costs; restore and tamper/replay/rollback test vectors; lost-device and compromised-key drills; snapshot completeness and retention validation; enforce disabled-by-default configuration until approval. No backup protocol is activated by PR #175.

Protocol references: [W3C WebAuthn Level 3 PRF extension](https://www.w3.org/TR/webauthn-3/#prf-extension); [Chromium virtual authenticator PRF support](https://chromedevtools.github.io/devtools-protocol/tot/WebAuthn/). These describe primitives/test capability; they do not establish that CF Meet implements protected unlock.
