# Optional encrypted account-history backup — implementation proposal

Status: proposed only; security review and owner activation approval required. No backup capability is activated.

## Separate optional encrypted account-history backup proposal

Backups remain off. This proposal is not a production capability or implemented protocol.

Generate a client-controlled random recovery root with at least 256 bits of entropy; provide an explicit owner-approved recovery artifact and verify it can restore before relying on it. Derive a versioned backup wrapping key with domain separation; encrypt a random per-snapshot data key and authenticate manifest/chunks and account/snapshot/version bindings. Store only authenticated ciphertext and opaque storage references on the service. Never send the recovery root, unwrapped keys or plaintext archives to servers or telemetry. Prefer random recovery material over a low-entropy password; any password-derived option requires reviewed memory-hard KDF parameters, salt and offline attack analysis. No silent escrow or account-password fallback.

A new device signs in normally, obtains account-scoped backup ciphertext, and locally uses the recovery secret to verify/decrypt the manifest and all chunks. Device authorization is necessary but does not replace the recovery secret. Password reset changes online authentication only: it cannot decrypt an old backup. Losing all valid device copies and the recovery secret is unrecoverable; disclose this before activation. A stolen recovery secret plus backup ciphertext compromises that backup; rotate recovery material and rewrap/re-encrypt retained snapshots, revoke obsolete access, and assess already downloaded copies, which cannot be remotely erased.

Rotation: version recovery roots and wrapped snapshot keys, bind the version in authentication, checkpoint rotation and verify a new restore before retiring the old wrapping record. Retention/deletion: owner-selected finite snapshot retention, hard byte quota, encrypted tombstones and object cleanup, legal/retention policy review, documented replica/backup expiry; user deletion cannot revoke copies already downloaded. Treat manifest metadata and access logs as sensitive. Backup storage cost is approximately retained ciphertext bytes plus manifests/chunk overhead, replication and egress; deduplication must not expose plaintext-derived cross-account identifiers. Before pricing, measure actual ciphertext growth and restore bandwidth; no fabricated monetary estimate is provided. Native secure storage and recovery UX need iOS/Android implementation and physical-device tests.

Acceptance gates: independent cryptographic/protocol review; owner approval of recovery-key UX and costs; restore and tamper/replay/rollback test vectors; lost-device and compromised-key drills; snapshot completeness and retention validation; enforce disabled-by-default configuration until approval. No backup protocol is activated by PR #175.

## Account-level incremental backup engineering plan

This plan is inactive and requires cryptographic review before activation. Account-level history availability is mandatory; an optional backup is one eligible recovery source, alongside authorized devices. The application must automatically look for eligible sources when a new device is authorized and must explicitly record partial/empty/unavailable coverage rather than presenting one archive as complete account history.

### Data model and incremental snapshots

Use an encrypted account-history manifest with a version, random backup-generation ID, snapshot ID, previous-manifest digest, authorized source device identity, covered conversation/member intervals, immutable message IDs, source sequences, and explicit coverage gaps. Model edits, reactions, deletion tombstones, replies, read positions and conversation metadata as versioned encrypted records with deterministic conflict rules; do not infer that a source has all account history merely because its local cursor reached the server tail. Attachment descriptors/content keys remain inside recipient-encrypted backup chunks; store attachment ciphertext separately under unguessable opaque object IDs and retain only the objects referenced by live eligible manifests.

Each incremental snapshot consists of immutable bounded chunks (candidate decoded maximum 256 KiB), a manifest of ordered authenticated chunk hashes and record coverage, and a signed/authenticated chain to the prior accepted manifest. Use client-controlled random recovery material and separately derived encryption/authentication domains and fresh per-chunk keys/nonces through reviewed primitives. No cross-account plaintext hash/deduplication identifier. Any within-account deduplication must use a secret-domain-derived identifier and undergo leakage review. Never silently advance an incremental watermark when a source only uploaded a partial page: advance only after encrypted objects and the final manifest are durably acknowledged and client-verified.

### Scheduling and device authority

The client schedules an incremental backup after a bounded change batch and a candidate 15-minute idle interval while unlocked and online; retry with bounded backoff/jitter and respect bandwidth, battery and storage budgets. Browser closure can suspend this schedule; do not promise server-side execution of a task that needs client-held secrets. Native scheduling uses OS-approved background facilities and secure-storage policy. A server may schedule opaque object cleanup and track encrypted snapshot status but must never decrypt or construct message backups.

Authorize upload, listing, download and deletion using a live account session plus installation/device proof, scope and non-revoked device authority. Backup authorization is independent of the recovery secret: a stolen account login alone must not decrypt old backups. Bind each upload to the source device and generation. Revocation ends future upload/download authority and cancels in-progress work; already downloaded ciphertext/recovery credentials cannot be remotely erased. New devices initiate discovery automatically after fresh authorization, then locally request the required authenticator/recovery credential; absence of that credential is a real blocker, not successful restoration.

### Restoration and reconciliation

Restore first verifies account/generation/source bindings, the manifest chain, signature/authentication, quotas and complete chunk inventory. Fetch/decrypt in bounded pages, verify each chunk, and commit the imported records with the resume checkpoint in one encrypted local transaction. Preserve readable local records and immutable message identities, apply deletions/edits according to authoritative visibility rules, and reject rollback to an older accepted manifest. Report missing chunks, skipped records, unavailable attachment objects and inconsistent coverage as partial recovery. Resume from the durable checkpoint after interruption, revalidate device authorization on every network phase, and clear transient recovery material when the operation locks or completes.

Do not grant historical MLS epoch secrets to a new device. Restore authorized encrypted record copies and their attachment metadata instead. Historical membership and per-user visibility must be checked before constructing/exporting a snapshot and rechecked when reconciling against current deletion/retention state. The source must not resurrect plaintext from a locally cached DECRYPTED record whose authoritative lifecycle has since become deleted, expired, purged, hidden or otherwise ineligible.

### Rotation, account recovery and compromise

Password/email/OTP recovery changes online account authorization; it never derives or replaces a lost backup root. Recovery-root rotation creates a new generation, rewraps or re-encrypts eligible snapshot keys with authenticated version binding, verifies a complete restore and only then retires the old wrapping records. Provide a separate revocation/compromise path with audited generation invalidation. If an attacker already possesses an old recovery root and ciphertext, rotation cannot revoke that historical copy. If every eligible device, backup copy and valid recovery credential is lost, recovery is impossible.

### Infrastructure, retention and cost gates

Proposed initial limits for review: 1 GiB encrypted backup quota/account, at most two concurrent transfers, a 30-day snapshot retention default, bounded page/chunk sizes and finite incomplete-upload TTL. These are proposed limits, not deployed settings or approved pricing. Enforce quotas before accepting object writes, authenticate object ownership, make object commits idempotent, and garbage-collect only unreferenced expired objects after a safety window. Propagate account/backup deletion through active object indexes, replicas and retained snapshots with documented provider backup expiry and audit completion; do not claim deletion of copies already downloaded to devices.

Capacity planning must measure encrypted bytes per account and change rate, manifest/chunk overhead, replication multiplier, retained generations, object-request rate, restore egress and concurrent resume workloads. Estimate monthly storage as retained ciphertext GiB multiplied by the actual provider's approved GiB-month rate, plus request, replication and egress charges. Obtain current provider quotes and owner cost approval before activation; no monetary amount or unbounded free quota is assumed. Include alerts for quota pressure, object/manifest inconsistency, failed cleanup, repeated partial restores and unusual recovery access using privacy-preserving metadata only.

### API/database/SDK work packages and review gates

Add versioned backup capability negotiation; generation/snapshot creation and authorization; bounded chunk PUT/GET; manifest commit; status/coverage/resume; key-generation rotation; and deletion APIs. Store only opaque encrypted objects, ownership/scope, size/digest, expiration and auditable progress in additive schema changes. SDKs share archive formats and validation vectors; web, Android and iOS must implement secure key handling and actual restore flows, not merely expose crypto primitives.

Required review artifacts: formal threat model; key hierarchy and domain-separation specification; canonical manifest/chunk serialization and binding vectors; replay/rollback and source-substitution tests; entropy/KDF review; interrupted restore/rotation/deletion drills; real five-device history reconciliation; unsupported/lost authenticator handling; quota/retention/cost review; and proof that no server or telemetry path holds plaintext or decryption roots. Keep the protocol disabled until these reviews and the owner's activation approval are recorded.
