**Source examined:** isolated checkout of GitHub `main` at `947f29514e93e0a813622105ecf6662c22495ca6`; line numbers below refer to that revision. This is an investigation, not a production certification. No application code, account, device, message, key or production configuration was changed.

## Executive summary

**CONFIRMED (source):** Normal web logout explicitly attempts to revoke the local Messaging device and wipe its locally encrypted history and keys. A subsequent enrollment can therefore create a new Messaging identity even in the same browser. This is a concrete availability risk and a plausible explanation of the report, not proof of the incident trigger. Separately, the worker labels an unprocessed received message `BEFORE_JOIN` simply when its epoch is lower than the device's *current* group epoch. The UI also labels certain failed or waiting messages by comparing creation time to Messaging device registration time. These are heuristics, not proof of when this browser or device first joined a particular group or whether another device can supply the history.

**NOT VERIFIED (incident):** No affected account identifier, message identifiers or incident time window were supplied. We could not inspect the production VPS, database, device records, account sessions, Messaging logs, browser IndexedDB or the affected browser. Consequently the event that caused access to be lost, affected ciphertext existence, original device status, current frontend/backend image SHAs, and incident recovery cannot be established. Do not interpret the warning or this source review as proof of logout, browser replacement, erased storage, or an MLS failure. The exact incident stage of loss remains unknown.

**SUSPECTED:** A re-enrollment following logout, session/device revocation, browser limit eviction, or local state loss could lead to a later registration date and unavailable earlier group epochs. Another hypothesis is incorrect classification after state/cursor advancement, including an earlier-epoch message that the device had joined in time to receive. Evidence must discriminate these paths.

## Frontend classification

- **CONFIRMED:** `apps/web/messaging-crypto/worker.src.js:523-598`: `processMessages` sorts by sequence and skips sequence at or before its persisted cursor. Removed messages and commits take separate paths. An own-device message uses a sealed pending record, or becomes `SENT_ELSEWHERE` if none exists. For a different sender device, `m.epoch < Number(device.epoch(gid))` produces `BEFORE_JOIN` without attempting decryption or checking the actual epoch at which this device joined. Other processing errors become `FAILED`. Outcomes and cursor are sealed and persisted with the device state in one transaction. A lower current epoch comparison does not, by itself, prove the device never had access at that old epoch, nor that a retained local copy is unavailable. Whether this branch caused the reported messages is **NOT VERIFIED**.
- **CONFIRMED:** `apps/web/src/lib/messaging/engine.ts:1896-1910, 1982-2017` obtains `deviceRegisteredAt` from the Messaging device directory (`:591-600`). A `BEFORE_JOIN` record gets the warning. An otherwise failed record with `createdAt < deviceRegisteredAt` also gets it; a not-yet-in-group active waiting message before that timestamp gets it even without a decryption attempt. Date parse failures make the timestamp comparison false. Registration time is not group join time or proof of data loss. Sent and received messages can pass through these UI branches. `e2ee-membership.ts:113-133` uses a similar timestamp test for the chat preview.
- **CONFIRMED:** The additional sentence about bringing history from another device is selected when the active Messaging device directory contains another device (`engine.ts:1908-1910, 1421-1425`), not when that device is online, has the relevant records, or can actually complete transfer. The cache can be up to 30 seconds old. Thus the sentence does not guarantee recoverability.
- **CONFIRMED:** `worker.src.js:274-322` opens an account-scoped IndexedDB device envelope using a non-extractable AES-GCM wrapping key and returns `NONE` when no device envelope exists; `engine.ts:603-636` creates and adopts a new device during auto-enrollment. Account installation identity is separate and generated/stored in IndexedDB (`apps/web/src/lib/auth/account-device-core.ts:134`, `account-device.ts`). `account_devices.rs:1108-1133` normally reuses a non-revoked same installation with the same key. Account and Messaging device IDs must not be equated.
- **CONFIRMED:** `worker.src.js:131-134, 280` uses a per-account Web Lock; another tab is reported locked (`engine.ts:480-495`) rather than deliberately enrolling a second device. Refresh, closure, frontend/worker update, and ordinary session refresh are **NOT VERIFIED end-to-end**; the code's durable open path alone cannot exclude a migration, eviction, interrupted registration or race. `engine.ts:497-507, 580-585` wipes local state and can re-enroll when a successful device directory response says the local device is not active. Request failures propagate to the surrounding error handling; do not assume a transient error necessarily produces an inactive result.

## Logout, sessions, and revocation

- **CONFIRMED (source):** `apps/web/src/services/auth.service.ts:123-128` invokes `signOutMessaging()` before the logout request; `signout.ts:12-46` attempts revocation and wipe through the running engine or a worker and bounds waiting to five seconds. `engine.ts:887-901` stops background work, attempts `identityApi.revokeDevice`, then attempts worker `wipe`. These are best-effort paths, so a source audit does not prove every logout successfully completed either step. The non-engine fallback and lock contention also need end-to-end testing. `worker.src.js:784` implements wiping. Session ending and explicit device revocation must be distinguished from local wipe.
- **CONFIRMED (architecture):** ADR 0057 amendment A1 describes session/device fan-out, while ADR 0060 establishes a persistent account device separate from an account session, and ADR 0067 revokes the least-recently-used web account device at the configured limit (default four in ADR 0060). The latter can end its sign-ins and downstream credentials. These are documented mechanisms, not evidence they occurred in this incident. ADR 0066 documents prior missing-device/KeyPackage delivery failures and external self-join; deployment and incidence are unverified.
- **CONFIRMED (source):** `services/meeting-service/src/services/communications.rs:451-461` fans an ended account session to `unified_messaging/identity.rs:280-318`; Messaging `realtime/session_devices.rs:281-345` handles session devices and bound client sessions. This path must be distinguished from persistent E2EE device revocation and Hub-linked device fan-out. Do not infer that every token refresh or natural expiry revokes a persistent E2EE device without tracing the actual event and records. `account_devices.rs:773-821` implements account web device eviction and emits an event; actual configured limits and victims are **NOT VERIFIED**.
- **SUSPECTED:** Coupling logout to destructive Messaging-device removal is an architectural contributor to history loss. An end-user sign-out and a lost/compromised-device removal have different availability needs, but any change must retain revocation guarantees and authenticate re-entry. The report cannot determine whether this coupling triggered the incident.

## Encryption and delivery lifecycle

**CONFIRMED (source design):** Private application messages are MLS ciphertext. Sender/group membership, active device additions and KeyPackage stock are coordinated by the web engine and ADR 0066. `services/messaging/src/messages/e2ee.rs:1-9, 84-115, 132-186` describes/checks public framing and current epoch and persists opaque ciphertext, not server plaintext. `services/messaging/src/mls/mod.rs:199-209, 349-439, 518-526, 646-672` governs commit epochs, current GroupInfo and device Welcomes. The web worker processes ciphertext and persists locally sealed records and cursor (`worker.src.js:523-598`); the engine renders these or metadata-only waiting placeholders. Sender messages depend on the local sealed pending copy (`worker.src.js:565-573`). The transfer archive is distinct from restoring old MLS epoch secrets.

**NOT VERIFIED:** The affected sender's encryption epoch, the recipient's leaf membership at that epoch, server acceptance and ciphertext retention, per-device delivery, Welcome and KeyPackage state, cursor, local decryption, and local persistence. Consequently none of missing keys, KeyPackages, Welcome, epoch mismatch, storage loss, failed migration, timestamp defect, delivery/sync failure, revocation or UI misclassification can be identified as this incident's actual cause. An external join cannot retroactively grant old MLS epochs (ADR 0066), but that architectural fact does not prove this device was absent when the affected messages were created.

## Recommendations and safeguards

1. **SUSPECTED, pending evidence:** Separate ordinary authentication session termination from persistent encryption identity destruction. Preserve encrypted local state and persistent device identity across normal logout/session renewal under an explicit threat model and reauthentication policy; reserve terminal revocation and key erasure for explicit device removal, sign-out-and-forget, compromise, or another clearly defined policy. Align Account, Hub and Messaging fan-out contracts; do not silently resurrect revoked identities. Assess shared-device confidentiality before choosing local retention and define clear opt-in/forget behavior without weakening E2EE.
2. **CONFIRMED design concern:** Replace the lower-than-current-epoch and registration-time inferences with accurately tracked group join/epoch and processing provenance. Distinguish missing keys, pending sync, failed decrypt, unavailable historical epoch and imported/local copies. Do not overwrite recoverable local records or advance a cursor past a transient failure without a safe retry strategy. Preserve confidentiality and avoid changing warning text as a substitute for fixing the underlying cause.
3. **SUSPECTED:** Improve history availability with an authenticated, verified, resumable device-to-device transfer and, if product policy authorizes it, optional end-to-end encrypted backup with client-controlled recovery keys. No server plaintext or server-held decryption key. Bound archives, partial transfers, attachment keys, conflicts, verification, revocation and key rotation need explicit protocol and threat-model review. No previous device or recovery key means old MLS ciphertext alone may remain unrecoverable.
4. **NOT VERIFIED until design:** Database/API changes may require persistent device-to-installation bindings, session-independent device lifecycle, group membership/join provenance, durable delivery/processing state and auditable redacted reason codes. Version contracts additively; preserve existing ciphertext, device rows and history; safely handle old clients, already-revoked terminal devices, concurrent tabs, partial enrollment and rollback. Do not issue destructive migrations. Determine what historical evidence can and cannot be reconstructed before migration.
5. **Required regression suite:** all scenarios in the matrix, both send directions and private direct/group conversations, managed isolation, stale/old-epoch messages after a valid join, out-of-order sync/commits, cursor failure/retry, timestamp skew, logout interrupted or with another tab holding the lock, session refresh/expiry versus explicit revocation, device limit eviction, KeyPackage exhaustion, missed Welcome, deployments and worker upgrades, encrypted transfer with unavailable/empty sources, archive bounds, attachment recovery, and no plaintext/key leakage. Run controlled full-stack journeys in addition to unit tests, then validate against sanitized production evidence.

## Security implications

**CONFIRMED:** MLS forward secrecy and client-held keys constrain recovery: a service retaining ciphertext does not automatically have the means to decrypt it. Local retention, backups and transfer expand the exposure window or attack surface and require explicit authorization, device authentication, integrity, revocation and recovery-key design. Automatic browser trust after fresh sign-in and LRU eviction are deliberate ADR 0067 policy decisions with availability/security tradeoffs. **NOT VERIFIED:** any compromise, unauthorized device, key leak, or production data loss in this incident.

### 1. False historical non-membership and unavailable old epoch

**CONFIRMED:** `worker.src.js:574-575` equates `message.epoch < device.currentEpoch` to `BEFORE_JOIN`; no join epoch is consulted. The test receiver demonstrably was a member at the old message epoch. The hypothesis that every such message predates device membership is disproven at the worker boundary. Its cursor moves to the classified message (`:592-597`) and repeated processing is skipped (`:537`).

**CONFIRMED limitation:** the independent direct-core test also refused the old message after merging a commit. `packages/messaging-crypto/src/group.rs:127-131` creates groups with the builder configuration; join paths use `MlsGroupJoinConfig` (`:293`, `:335`); this investigation has not established a safe past-epoch retention window. Runtime evidence proves rejection under the shipped configuration, not the exact upstream error subtype or that every possible older ciphertext is unrecoverable. Calling `device.process` instead of assigning `BEFORE_JOIN` alone is insufficient to fix this reproduction.

**SUSPECTED production pathway:** a group state advance outside processing the entire pending application backlog, lost local copies, Welcome/external join at a newer epoch or interrupted synchronization could make this issue reachable. Normal `engine.ts:1814-1874` serializes per-conversation sync, fetches after the worker cursor and processes pages in order; the test intentionally advances state before pending backlog through the real worker API. It does not prove that ordinary production offline catch-up violates this ordering. The device must process a complete ordered backlog before throwing away any old epoch material needed for that backlog, or retain a bounded, explicitly reviewed recovery capability. Actual production membership, old epoch state and delivery order remain unknown.

### 2. Cursor acknowledges processing attempts rather than successful durable recovery

**CONFIRMED:** `worker.src.js:589-597` catches a decryption failure, seals the error, advances `last`, and persists it as the conversation cursor. `:537` suppresses every subsequent attempt at or below it. `engine.ts:1839-1842` asks the backend for messages after that same cursor. There is no successful-decryption cursor or retry queue in this path. The replay test confirms a corrected processing opportunity is suppressed. The across-call reordering test confirms missing lower sequences are skipped after a higher one; that is a robustness gap conditional on a missing/gapped page, not evidence that the backend currently returns such pages. Preserve transport deduplication while separately tracking processing state and terminal versus retryable failures.

### 3. History export is incomplete without an explicit completeness contract

**CONFIRMED:** `worker.src.js:683-705` loads records, traverses keys in reverse, filters to `DECRYPTED`/`SENT`, and breaks when the next serialized record would exceed `MAX_ARCHIVE_BYTES`. IndexedDB key order is account/conversation/sequence order, not global recency. Thus the export can favor lexicographically later conversations; the observed single-conversation run dropped older records. The return value has sealed bytes and conversation count, without continuation or completeness. Import `:708-730` imports exactly the returned records. The 44-to-32 result is omission from the transfer, not deletion from its source.

**CONFIRMED:** an empty source produces a valid archive. `engine.ts:2766-2793` selects sources by ACTIVE directory status; neither that nor the warning sentence establishes source coverage. Manual transfer may recover only the subset a source retains. A successful handshake is not evidence of complete history recovery.

### 4. Logout destruction

**CONFIRMED primitive and source integration:** `auth.service.ts:123-128` invokes Messaging sign-out, `engine.ts:888-901` attempts revoke then wipe, and `worker.src.js:784-800` erases the account's wrapping key, device envelope, records and pending storage. The real worker confirms disappearance of identity and history, followed by empty re-enrollment. **NOT VERIFIED:** actual local Account/Hub session fan-out, ordinary logout completion, the five-second fallback, cross-tab races, and whether this triggered the reported production incident. Account installation persistence must not be inferred from a worker ID change.

## Permanent remediation architecture (design; no implementation approval implied)

All proposals below are **SUSPECTED remedies pending design/security review and full-stack validation**. They address reproduced mechanisms but do not establish the production trigger.

### Identity, sessions and protected persistence

Account session, Account installation device, persistent Messaging device, MLS leaf per conversation, and client/realtime session must be distinct identities with explicit lifetimes. Normal sign-out ends authentication/client sessions and clears live bearer/worker memory; future access requires authenticated authorization for the same unrevoked device. Terminal device removal ends authority, queues MLS removal and destroys the appropriate local state. A revoked device is never reactivated. Session refresh/expiry must not implicitly re-enroll a persistent Messaging device. Hub and Account fan-out need explicit `SESSION_ENDED` versus `DEVICE_REVOKED` semantic contracts, not shared destructive handling. Logout-everywhere/compromise behavior must remain explicit and consistent across old/new clients.

Preserving an IndexedDB CryptoKey by itself is not a sign-out lock: same-origin script may still use it. The retention design must specify shared-device expectations, how encrypted history is unlocked after fresh authentication, local key wrapping/OS protection, and how forgotten/compromised devices are purged. No server-held plaintext or server decryption key. A forgotten device can enroll afresh but needs an authorized transfer/recovery path to retrieve history; terminal revocation cannot be undone. Existing UI/UX changes are outside this investigation.

### Membership, delivery and cryptographic state

Persist authenticated per-group join provenance with the device state: initial joined epoch, join method/Welcome or external commit reference, local membership intervals/removals, processing version and relevant cursor checkpoint. Treat absent provenance on legacy state as unknown. Never backfill historical non-membership from registration timestamps. Distinguish missing group state, waiting Welcome, missing/expired epoch secret, failed integrity/AAD, revoked device and absent local copy. Do not relabel a failure as pre-join without evidence.

Introduce separate durable fetch/receipt position, contiguous processed watermark and per-sequence retry state. Store ciphertext references plus stable metadata for retries without server plaintext. A failed application record must not make a later successful opportunity unreachable. Commit sequencing and group-state persistence must be atomic with durable record outcomes; do not replay commits blindly or fork the group. Process the full required backlog before epoch advancement where possible. Choose and audit a bounded MLS past-epoch/ratchet retention policy for offline and out-of-order delivery. Longer retention affects forward secrecy and replay handling; it requires protocol/crypto tests and deliberate limits rather than simply retaining every epoch forever. Authenticated duplicate detection and immutable message IDs must survive retries and rollback.

### History synchronization, transfer and backups

An authorized device should advertise authenticated coverage metadata rather than merely ACTIVE status; it must not reveal message contents. Automatic transfer needs device authorization, transparency verification, revocation checks, consent/security policy, rate limits and explicit source/target binding. Native and web must share the archive format and record identity semantics. Current signed comparison-code transfer remains the baseline until a new protocol is reviewed.

Replace the monolithic archive with a versioned authenticated manifest and bounded chunks/pages, a stable snapshot, continuation cursor, total counts/ranges, explicit partial coverage, chunk digest/order/completeness binding, expiry, target/source/principal/scope binding and resumable acknowledgments. Import idempotently into encrypted local storage, respect deletions/visibility/retention, preserve attachment key protection, and refuse mixed-source/snapshot substitution or rollback. Server stores only sealed chunks; never decrypted archives or recovery keys. Completion must mean verified manifest coverage, not merely one successful import. Transfer absence or an empty source is a coverage result, not success recovering missing messages.

Optional backups require a separately versioned client-controlled recovery-key protocol, authenticated encryption, KDF/entropy choices, snapshot integrity/rollback protection, key rotation, deletion/retention and compromise semantics. The repository includes lower-level backup vector tests, but this is not evidence of an operational browser cloud recovery service. Password reset must not give the server an old-history decryption capability. Loss of all valid source copies and recovery keys remains unrecoverable.

### Required components and compatibility

- Frontend/worker: preserve identity only according to approved session/retention policy; record membership provenance; split processing cursors; retry failures safely; verify paginated coverage; handle partial/empty history explicitly. Retain current encryption boundaries and worker integrity.
- Account/Hub/Messaging backend: precise lifecycle events, durable idempotent outbox delivery, persistent installation binding distinct from session credentials, safe eviction policy and audited reasons, explicit Welcome/epoch/delivery metadata and bounded resumable sealed transfer APIs. Device revocation remains terminal.
- Database: additive fields/tables for lifecycle version, device-binding lineage where available, transfer manifest/chunk/session metadata and progress. No plaintext history. Local IndexedDB migration must preserve sealed records and keys, be transactional and rollback-safe; unknown legacy provenance must stay unknown. Do not rewrite server ciphertext or resurrect revoked rows.
- SDK/cryptographic protocol: versioned archive/chunk format, proofs and state serialization shared across TypeScript/Rust/Dart/native; test old state import, per-platform secure storage, suspended/offline clients and key protection. The current mobile app MANAGED path is not a deployed private-history synchronization implementation. iOS/Android operational parity requires actual app and physical-device testing.
- API: additive capability negotiation and explicit incomplete/coverage/pagination contracts; old clients continue reading their existing format. Gate writes to the new transfer format by negotiated capability. Mixed-version revocation and session events must fail closed without wiping retained state accidentally. Rollback must leave old data readable and preserve terminal revocations. No destructive bulk cleanup during migration.
